- **Part C（10-25 → 11-02）历史推理可见性**：回传 vs 屏蔽对分数 / 步数 / 成本的影响、1.0.0 计数 bug 的根因与修复、DeepSeek tool-call 模式、四格对比、对数据采集的含义。

**三部分合起来的结论**：

1. 成本的大头是输入重发（flash 73%）或输出推理（dsv41 68%），缓存命中 96.7%；失败轨迹花掉一半以上的钱。

4. harness 1.0.0 把模型看不到的历史推理也计入上下文估算（虚高 2.7–3.8×），提前摘要；usage 计数修了大头，"看不到"情形下的 P+C−R 修正仍未发布。

## A2. API 计费逻辑：为什么单条轨迹输入是 M 级

Terminus 是无状态的 chat-completions 循环，**第 k 次调用把完整对话历史作为 prompt 重发**：

```
call 1:  prompt = system+task                        (≈1.7k)
call 2:  prompt = system+task + a1 + obs1             (≈2.3k)
call k:  prompt = system+task + Σ_{j<k}(a_j + obs_j)  线性增长
累计输入 = Σ_k prompt_k ≈ 末轮长度 × 步数 / 2
```

实测（我们一条 flash 轨迹，API 真实 usage）：

| 调用 #      | prompt     | cached | 命中率 | 输出  |
| ----------- | ---------- | ------ | ------ | ----- |
| 1           | 2.4k       | 0      | 0%     | 191   |
| 2           | 3.1k       | 2.0k   | 67%    | 248   |
| 5           | 8.6k       | 5.4k   | 62%    | 1,127 |
| 10          | 21.2k      | 16.4k  | 77%    | 911   |
| 66          | 55.9k      | 49.2k  | 88%    | 9,146 |
| 130（末轮） | 114.6k     | 112.9k | 99%    | 454   |
| **累计**    | **12.34M** | 11.9M  | 96%    | 579k  |

12.34M / 115k（末轮）= 108 ≈ 130 / 2，完全符合线性累加。文件里去重只有 ~115k token，API 计费是它的 **100 倍**。

TH-3K 第 1 条同样复原：56 条消息、去重 139k，28 次调用累计 1.77M（13×）。

**缓存命中按步数的曲线**（全体平均）：

| 步 #  | 1   | 2   | 3   | 5   | 10  | 20  | 40  | 80  |
| ----- | --- | --- | --- | --- | --- | --- | --- | --- |
| flash | 1%  | 42% | 54% | 71% | 83% | 93% | 97% | 95% |
| dsv41 | 24% | 59% | 59% | 78% | 92% | 96% | 95% | 96% |

每轮只有「上一轮的输出 + 新的终端回显」（~0.6–0.8k token 回显 + 0.7–1.2k 输出）是未命中，而前缀越来越长，所以命中率单调逼近 100%。DashScope 隐式缓存以 1024 token 为块（`cached_tokens` 全是 1024 的倍数）；dsv41 第 1 步的 24% 是 system prompt 跨题命中。

**累计输入的分布**：69%（flash）/ 64%（dsv41）的累计输入花在后半段步数上。`累计 / 末轮 = 77` 大于 `步数 / 2 = 47`，因为上下文到顶（flash API 视角 ~210k、dsv41 ~70k，原因见 §A6.1）后 harness 做摘要重置，长尾轨迹（max 3035 步）在天花板附近反复重发。

## A6. TerminalHorizon-3K：补充说明

可训练部分的表见 §A3.2（与 flash / dsv41 并排）。TH-3K 特有的几点：

- 首条 user 消息（system prompt + 任务描述）只有 ~1.6k，user 侧 token 几乎全是终端回显。
- 平均 53 轮、末轮 ~139k，与我们 flash 成功轨迹（50 轮、108k）同量级，基本就是「过滤后保留成功轨迹」的形态。
- 文件 1.7 GB ≈ 3.5 字节 / token，与 490M 吻合。
- **三个数字的口径要分清**：训练用去重后的 490M（可训 324M，其中 think 250M）；API 口径的 20B 输入 / 324M 输出只是「如果重新采集一遍要付多少」。

### A6.1 为什么 TH-3K 按 256k 窗口训练还要剔除轨迹

Terminus 的上下文上限是 **262,144**（`TERMINUS_MODEL_CONTEXT_LIMIT`），所以**任何一次 API 调用的 prompt 不会超过 256k**（实测 flash 末轮 max 236k）。但轨迹文件记录的是**整条对话的全部消息**，而 Terminus 在接近上限时并不停，而是做 **context summarization**（Harbor `_summarize` / `_check_proactive_summarization`：空闲 token < 65,536 时，起一个子 agent 生成摘要 + 问答，把历史替换成摘要，继续跑）。摘要之后的新上下文从几 k 重新增长，但**被替换掉的旧消息仍留在 trajectory.jsonl 里**。于是：

```
单次 prompt ≤ 256k   但   轨迹总长 = Σ(每段上下文) 可以远大于 256k
```

TH-3K 实测（Qwen3.5 tokenizer）：整条轨迹 p50 139k、p90 307k、**p99 716k、max ~1M**；超过 256k 的 443 条（15.5%），超过 512k 的 83 条。`coding_sft` 的 `prepare_terminal_horizon.py --max-tokens 262144` 因此隔离了 321 条 over-long（11%，与 15.5% 的差是 tokenizer / 模板开销口径不同），剩 2,201 条进训练。

重置次数见 §A3.1 的表。dsv41 的重置是 flash 的 2.5 倍，**且触发时 API prompt 只有 49–101k（p50 72k），远没到 262k**。这不是窗口小——deepseek-v4.1-flash 官方上下文 1M，而且两个模型在平台上注册时都没设 context limit，harness 一律给 `TERMINUS_MODEL_CONTEXT_LIMIT=262144`、空闲 < 65,536 触发摘要，所以理论触发点都是 ≈ 197k。flash 实测触发在 205–219k，吻合。

dsv41 提前触发的原因是**本地计数与 API 计数不一致**：

|                                     | flash         | dsv41                         |
| ----------------------------------- | ------------- | ----------------------------- |
| 每步 Δprompt（API）p50              | 1,476 tok     | 983 tok                       |
| 每步 completion（API）p50           | 680 tok       | 1,129 tok                     |
| Δprompt / completion                | **1.73**      | **0.94**                      |
| Δprompt / (answer + obs 字符 ÷ 3.6) | 1.60          | 1.07                          |
| 历史字符数 / API prompt token       | 3.6（含推理） | **27**（含推理）/ 8.7（不含） |

flash 的 Δprompt ≈ 1.6 × (回答 + 回显)，多出来的正是上一轮的 `reasoning_content`——**Qwen 的 DashScope 端把历史里的推理算进 prompt 并计费**。dsv41 的 Δprompt ≈ 1.0 × (回答 + 回显)，**DeepSeek 的 DashScope 端把历史里的 `reasoning_content` 丢掉了**（不进上下文、不计费，这也是 DeepSeek 官方 API 的既定行为：多轮对话不回传上一轮的思维链）。但 Harbor 这边 `interleaved_thinking=true` 把每轮推理都留在 `chat.messages` 里，`_count_total_tokens()` 用本地 `litellm.token_counter` 对**含推理的全部消息**计数——dsv41 推理占历史字符的 70%，本地估出 ~400k「已用」时 API 实际只用了 ~73k，于是在 API 视角的 50–100k 就触发了摘要。

后果：dsv41 实际能用的有效上下文被压到 ~1/3，重置次数翻倍，成功率可能受损（§A4：失败轨迹 61% 有过重置）。修法是在 harness 里对 DeepSeek 路由关掉 `interleaved_thinking`（本地计数不再含推理，与 API 一致），或把 `TERMINUS_MODEL_CONTEXT_LIMIT` 按 1M 注册——两者都需要发新 harness / 模型版本。

**TH-3K 里一次摘要重置都没有**：2,852 条的 user 消息全是 `New Terminal Output` / `Current Terminal Screen` / `Previous response had warnings` / `Are you sure…`，没有任何 handoff prompt。也就是说论文作者**把发生过摘要的轨迹整个过滤掉了**（或采集时关了 summarization 并用更大的窗口），保证每条都是连续线性的对话。那为什么还有 15.5% 超过 256k？因为采集模型 DeepSeek-V4-Pro 的上下文是 1M，`TERMINUS_MODEL_CONTEXT_LIMIT` 按 1M 注册就不会在 256k 触发摘要——轨迹可以连续长到 p99 716k / max 1.2M。所以 TH-3K 的「超 256k 要剔除」与摘要无关，纯粹是**采集窗口（1M）大于训练窗口（256k）**。

我们的轨迹则相反：窗口 256k（dsv41 因计数偏差实际在 API 视角 ~70k 就触发），到顶就摘要，所以整条轨迹去重后超过 256k 的那部分一定跨越了摘要边界。3035 步那条是典型：prompt 从 1k 线性涨到 3020 步的 228k，摘要后掉到 8k，再跑 15 步，总墙钟 297 min 顶到 5 h 上限 — 单次调用从未超过 256k，但整条轨迹累计 378M 输入、去重后也远超 256k。

对 SFT 的含义：整条轨迹训练必须切在摘要边界（每段 ≤ 256k，且后一段的首条 user 是摘要而非原题），或直接剔除；`coding_sft` 选的是剔除（`--overlong drop`），不在中间截断，避免 JSON 动作被切半。

### A6.2 能否限制最大交互轮次

可以。Harbor Terminus 2 自带 `max_turns`（别名 `episodes` / `max_episodes`，默认 1,000,000 即不限），到达后结束 episode 并正常导出轨迹。当前 harness `cth-terminus-2-stream@1.0.0` 的 `inference_contract` 明确写了 **"no artificial max_turns"**，agent env 里也没有对应变量，所以现在的限制只有两道：

| 限制       | 值                                                               | 效果                               |
| ---------- | ---------------------------------------------------------------- | ---------------------------------- |
| agent 墙钟 | 5 h（`ttl_seconds=14400` + 平台 agent deadline，提前 60 s 收尾） | 3035 步那条就是被它停的（297 min） |
| 上下文     | 262,144，空闲 < 65,536 触发摘要                                  | 不停轨迹，只重置上下文             |

要加轮次上限需要**发一个新 harness 版本**（`cth-terminus-2-stream@1.0.1`），在 runner 把 `TERMINUS_MAX_TURNS` 透传为 `Terminus2(max_turns=...)`（runner 源码在 `opencode/terminus_stream/build/`，当前读的 `TERMINUS_*` 变量都在那里映射；加一个变量 + `suppress_max_turns_warning=True` 即可）。平台上已发布实体不可变，所以是升版本而非改现有。

该设多少——用已有轨迹模拟「跑到第 cap 步就停」：

| cap     | flash：被截轨迹 | 其中 score=1   | 输入 / 输出保留 | dsv41：被截轨迹 | 其中 score=1   | 输入 / 输出保留 |
| ------- | --------------- | -------------- | --------------- | --------------- | -------------- | --------------- |
| 64      | 619（48.8%）    | 217（17.1%）   | 46% / 64%       | 514（40.7%）    | 176（13.9%）   | 42% / 52%       |
| 128     | 287（22.6%）    | 76（6.0%）     | 73% / 85%       | 232（18.4%）    | 71（5.6%）     | 63% / 71%       |
| 192     | 125（9.9%）     | 34（2.7%）     | 85% / 93%       | 144（11.4%）    | 39（3.1%）     | 74% / 80%       |
| **256** | **65（5.1%）**  | **14（1.1%）** | **91% / 97%**   | **108（8.5%）** | **27（2.1%）** | **81% / 87%**   |
| 384     | 16（1.3%）      | 4（0.3%）      | 95% / 99%       | 60（4.7%）      | 16（1.3%）     | 91% / 94%       |

「其中 score=1」是被截的轨迹里最终答对的（占全部题的比例）——它们在第 cap 步时还没完成，截了就可能丢分，是上限估计（部分可能在截断前已经把答案写进文件）。

- **256 步**是合理默认：flash 最多损失 1.1% 的成功、省 9% 输入；dsv41 最多损失 2.1%、省 19% 输入（dsv41 步数更长尾）。
- 128 步省得多（27% / 37% 输入）但要赌 6% 的成功题，不划算。
- 轮次上限主要是**防死循环**而非省钱：成本大头是 p50 附近的正常轨迹，长尾只占 10–20%。

## A7. 误差与注意

- **无轨迹的题**（TIMEOUT / HARNESS_FAILED，~2%）和**重试 attempt** 不进统计 → 实际成本偏高 5–10%。
- 所有「单条 / 每题」数值除非标明 p50，都是 **mean = 总量 ÷ 轨迹数**；分布右偏，mean 比 p50 高 1.5–2 倍（flash 输入 8.6M vs 5.5M）。flash 的 `max 3035 步 / 378M 输入` 是一条死循环轨迹，把 mean 进一步拉高；成本估算用 mean（保守）。
- TH-3K 的 99.2% 命中是推算上限（按「上一轮 assistant 之前的前缀全命中」）；按实测曲线，真实约 97%，成本相应 +280 / +360 元。
- 两个在跑的 job（128 + 160 并发）共享 DashScope 隐式缓存，TTL 内高并发可能把命中率压低几个点：每掉 10 个点，flash +780、dsv41 +420 元。
- dsv41 若实际走阿里云挂的 `deepseek-v4.1-flash` 而非 DeepSeek 官方，以实际账单单价为准，公式不变。

| 64k 伤害的机制                   | 拖长到 5 h TTL（40%）  | 多次摘要丢信息（步数 p90 2.7×，TTL 只 2.5%） |

flash 对 compaction 更敏感的原因：它每步输出短（p50 657 tok）、靠大量短步累积状态，上下文是它的"工作记忆"；摘要一次就要重新 `cat`/`ls` 一遍。dsv41 每步推理长（p50 1.2k 输出）、步数少，上下文里冗余少，摘要丢失的比例也小。

## B5. 对训练数据采集的建议

1. **采集轨迹用 256k 触发 + max_turns 512**（即 `cth-terminus-2-stream@1.2.256`）。相比现行 1.0.0（262k 窗口 − 65k 阈值 ≈ 197k 触发、无 cap）：触发点往后推 60k，成本持平（2.04 vs 2.05 元/条），flash 分数 +0.01–0.04，重置轨迹从 33% 降到 ~20%（因为 `TOKEN_COUNT_MODE=usage` 不再过计）。
2. 若训练上下文是 256k，**不要用 512k 触发**去采：34% 的 flash 轨迹会超过 262k、21% 超过 300k，SFT 时要么截断要么丢（TH-3K 已经因为 1M 采集窗口丢了 15.5%）。256k 触发下超 262k 的只有 ~10% 的余量溢出（max 285k），`--max-tokens 262144` 过滤时损失可控；想零损失就把触发点设在 **224k**（256k − 余量）。
3. 不要指望 compaction 带来质量提升：没有任何一档比"不摘要"更好。摘要是**容量约束下的止损**，不是技巧。
4. 64k 档的轨迹（flash 平均 9.5 次重置、244 步；dsv41 3.0 次、p90 448 步）**不适合做 SFT 数据**：大量步数花在重置后恢复状态，是低信息量的重复动作；flash 40% 没做完。

## B6. 没覆盖到的 / 后续

- flash 64k 档还有 22 题在跑（全是 >4 h 的长题，大概率跑到 TTL）。它们进来后 64k 的 mean(DONE) 会再降一点，配对集合扩到 ~507，方向不变。
- 每档只 1 sample，相邻档差异都在噪声内。要分辨 128k vs 256k（差 0.00–0.016）需要 ≥4 samples/档（SE 降到 0.011），成本 ~4×；不建议——两档成本也一样，直接选 256k。
- 没测"不做 compaction + 硬截断"（context 爆了直接判 0）和"不同摘要 prompt"；也没测 `max_turns` 的其它值。
- dsv41 若要做同样的"长题"实验，应按 dsv41 自己的基线峰值重新抽题（≥96k 的只有 ~150 题）。

### B9.2 解读

1. **分数差 −0.02 在噪声内**（SE 0.021；dsv41 256k vs 512k 的噪声标尺也是 ±0.015）。屏蔽历史推理没有造成明显损失，也没有收益。去掉超时题后仍是 −0.024，方向一致但同样不显著。
2. **行为变了，而且和预期相反的方向**：每步 prompt 并没有明显变短（47k → 45k）。原因是 flash 本来每步推理就短（p50 675 token），历史推理在 prompt 里占比小；真正的差别是**模型在没有历史推理可参考时，每一步都重新推一遍**——completion 翻倍（p50 675 → 1,186）、单条推理字符 ×1.7。
3. **步数反而少了 28%，compact 少了 59%**。不是因为 prompt 变短触发得晚（峰值 95k vs 98k 几乎一样），而是每步花的时间翻倍（25 s → 49 s）、同样 5 h 内走不了那么多步：**TTL 命中从 18% 升到 24%**，而 fail 题的 agent 时长 p50 从 171 min 升到 196 min。步数少是被时间截断的结果，不是效率提升。
4. **成本**：输入省 32%（步数少），输出涨 41%（每步推理长），按 flash 价格折算后 **只省 6%**。和 §C1 里 4B 的结论一致：屏蔽历史推理省不下钱，输出单价是输入 3.4×，多出来的推理把省下的输入抵掉了。
5. 对 flash 这种"短推理、多步数"的模型，历史推理起的是**跨步缓存**作用——有它在，下一步可以直接接着上一步的结论走；没有它，每步都要从观测重新建立判断。dsv41 上游本来就丢弃历史推理（§C3），所以它的行为天然就是 nothink 模式——这也解释了为什么 dsv41 每步推理长（p50 3.6k chars）而步数少。

**结论**：训练/评测时是否保留历史推理，对 flash 的分数影响 <0.03，不构成选择依据；但**保留历史推理的轨迹更短、每步更快、单位时间内能完成更多任务**，采集数据时应保留（即 `TERMINUS_INTERLEAVED_THINKING=true`，1.2.96 默认）。

# Part C. 历史推理（reasoning_content）的可见性：回传 vs 屏蔽、计数 bug、DeepSeek tool-call 模式

日期：2026-10-25 → 11-02。本部分回答一个问题：**模型在后续每一步的请求里能不能看到自己前面各步的推理过程，对分数、步数、压缩次数、成本有多大影响；以及 harness 在这件事上有哪些坑。** 相关：[harness_comparison](../methods/harness_comparison.md) §A3（chat template 决定渲染）、[harness_comparison](../methods/harness_comparison.md) §B6（Qwen 模板的真实渲染）、§B9（flash 96k 屏蔽历史推理）、[trajectory_collection](../methods/trajectory_collection.md) Part B（三套 SFT 数据的对比）。

## C0. 结论先行

1. **对分数影响 <0.03，不构成选择依据。** Qwen3.5-4B/9B base 的 nothink 模板对照（TB2.1）、flash 1.2.96 vs 1.3.96（TH long128 512 题，+0.024，z +1.55）、dsv41 1.2.96 vs 1.4.96（−0.020，z −1.17）、dsv41 TB2.1 AB（−0.006）——全部不显著，方向还不一致。
2. **行为变化很大、而且两个模型一致**：看得到历史推理时每步推理只剩 1/3–1/4（flash 8.8k→3.8k chars，dsv41 10.7k→2.4k），步数 +30–40%，compact 次数 2.2–3.3×，累计输入 +27–47%，累计输出 −30–55%。历史推理起的是"跨步缓存"作用：有它下一步接着上一步的结论走；没它每步从观测重新建立判断。
3. **屏蔽历史推理省不下钱**：输出单价是输入的 3.4×，多出来的推理把省下的输入抵掉（4B：累计输入 −4~−20%、输出 +1.4~2.3×；flash：−6%）。
4. **harness 1.0.0 有计数 bug**：`litellm.token_counter` 把历史 `reasoning_content` 计入上下文估算，而模型看不到历史推理时这部分不占窗口 → 虚高 3.8×，真实用量不到一半就提前摘要。修复 = `TOKEN_COUNT_MODE=usage`（1.0.1 / 1.2.x 起）。但 usage 锚点 `P+C` 仍没扣掉"看不到"情形下的 R_N，所以 1.3.96（flash nothink）和 1.2.96（dsv41 普通 chat）两格仍提前触发（87% / 91% 的重置本不该发生）；修复代码在 `build/terminus_pkg_v4/` 未发布。
5. **DashScope 上的 DeepSeek 普通 chat 请求会在服务端丢掉历史 `reasoning_content`**；要让它看到，请求必须带 `tools` 且 `tool_choice != none`（harness 1.4.96 / 1.7.96 的 `TERMINUS_TOOL_CALL_MODE=function`）。**这条对 Qwen3.5 自家 sglang 不成立**：Qwen 模板只给"最后一条真 user query"之后的 assistant 渲染 `<think>`，观察作为普通 user 回传时历史推理一律不进 prompt，不论带不带 tools（[harness_comparison](../methods/harness_comparison.md) §B6）。
6. **对数据采集的含义**：目标模型推理时看得到自己历史推理（Qwen 系 SFT 后默认）→ 采集也用"看得到"的设置（flash 1.2.96+ / dsv41 1.4.96+），行为分布一致；否则训练上下文 ≠ 采集时模型看到的上下文（[trajectory_collection](../methods/trajectory_collection.md) §B1 脚注 ᵃ）。

## C2. harness 1.0.0 提前重置的根因与修复（10-26）

**现象**：nothink（DROP）端点由 `cth-terminus-2-stream@1.0.0` 评测。重置前一步的真实 prompt 只有约 12 万 token，占 262,144 窗口的 46%，按 `THRESHOLD=65536` 不应触发摘要。

**根因**：1.0.0 用 litellm `token_counter` 估算上下文，它把历史 assistant 消息的 `reasoning_content` 也计入了。但 nothink 模板不会把历史推理渲染进 prompt，所以这部分 token 实际不占窗口。在一条发生过重置的轨迹上，用真实模型 tokenizer 复现：

| | token |
|---|---|
| 1.0.0 估算（legacy） | 445,761 |
| 上游真实 `prompt_tokens` | 116,797 |
| 虚高倍数 | **3.8×** |
| 历史推理字符数 ÷ 3.53 字符/token | ≈ 447k（1,577,132 字符） |

差额正好等于历史推理的 token 数。估算超过 262,144 − 65,536 = 196,608 就会触发摘要，而当时真实用量还不到一半。

**修复**：发布 `cth-terminus-2-stream@1.0.1`（spec：`work/harness-specs/terminus-stream-1.0.1.json`，runtime 与 1.3.96 相同，都是 `pkg_v3`）。相对 1.0.0 只改了两项 env，窗口语义保持一致（`CONTEXT_LIMIT=262144`、`THRESHOLD=65536`、不限 `max_turns`，采样参数也一样），所以可以和 10-25 的 run 直接配对：

|---|---|---|---|
| `TERMINUS_TOKEN_COUNT_MODE` | （estimate） | `usage` | 以上一轮上游返回的 `prompt_tokens + completion_tokens` 为锚点，只估算之后新增的消息 |
| `TERMINUS_INTERLEAVED_THINKING` | （true） | `false` | 不再把历史 `reasoning_content` 发回模型，和 nothink 模板的实际渲染一致；当前步推理照常生成并写进 `trajectory.jsonl` |

验证：同一条轨迹上，usage 模式的估算/真实 p50 为 **1.003×**（legacy 是 3.8×）。

**规则**：凡是评测时模型看不到历史推理的（nothink / mask 类模板、DeepSeek 这类上游会丢弃历史推理的模型），一律用 1.0.1，不要再用 1.0.0。1.0.0 会在真实用量不到一半窗口时就提前摘要，导致步数和重置次数虚高。需要 96k 窗口 + `MAX_TURNS=512` 的场景，用同样带两项修复的 `cth-terminus-2-stream@1.3.96`。

## C3. 让 DeepSeek 看到历史推理：tool-call 模式（10-26）

> **11-02 补充（重要）**：下面「带 tools 且 tool_choice≠none 就渲染」是 DashScope dsv41 路由上的结论，**对 Qwen3.5 自家 sglang 不成立**。Qwen 模板只给「最后一条真 user query」之后的 assistant 渲染 `<think>`，而观察作为普通 user 消息回传时它就是最后一条 query，所以 Terminus 全系（含 1.4.96 的 `terminus_action` 开关）在 Qwen 上历史推理一律不进 prompt（token 计数增量 0）；只有观察以 `tool` role 回传（DSH 形态）才渲染（+2102）。抓包、模板、计数三层证据见 [harness_comparison](../methods/harness_comparison.md) §B6。顺带：Qwen 评测的 usage 锚点 P+C 也因此全部虚高（没扣 R），不只是 nothink 模板。


**问题**：DashScope 路由的 `dsv41-flash-1017` 在普通 chat 请求下会在服务端丢掉历史 assistant 的 `reasoning_content`（API 探针：塞 3000 token 假推理，`prompt_tokens` 不变）。也就是说此前所有 dsv41 的 Terminus 评测里，模型每一步都看不到自己之前的推理。

**发现（网关探针，模型 `dsv41-flash-1017-dashscope`）**：

| 请求形态 | 历史推理是否渲染进 prompt |
|---|---|
| 普通 chat（无 tools） | 否（+0 token） |
| `tools` + `tool_choice:"none"` | 否（+0） |
| `tools` + `tool_choice:"auto"` | **是**（+3001；两轮推理 +6002） |
| `tools` + 强制指定 function | **是**（+3001），且流式/非流式一致 |

历史消息本身保持原样（assistant 带 `content` + `reasoning_content`，观察仍是 user 消息）即可，只要请求带 `tools` 且 `tool_choice` 不是 `none`，服务端模板就会渲染历史推理。另外注意：assistant 带 `tool_calls` 后面直接跟 user 消息（没有 tool 回包）会被 DashScope 400 拒绝，所以历史里不能放 `tool_calls`。

**实现：`cth-terminus-2-stream@1.4.96`**（spec `work/harness-specs/terminus-stream-1.4.96-toolhist.json`，runtime `pkg_v4` = `uploads/261026/c56a02674c3227b1/pkg_v4/`）。与 1.2.96 的唯一差异是 `TERMINUS_TOOL_CALL_MODE=function`（新 env，默认 `none` = 1.2.96 行为）：

- 主循环的每次请求附带一个强制调用的 `terminus_action` function（参数 schema 就是 Terminus 的 JSON 回复格式：analysis/plan/commands/task_complete）。模型的动作以 tool_call arguments 形式返回，`lite_llm.py` 在 content 为空时把 arguments 当 content，下游 JSON parser 原样工作。
- 历史消息形态不变（user 观察 + assistant content + `reasoning_content`），`interleaved_thinking=true`。
- 摘要三个 subagent 的请求**不带 tools**（它们要自由文本输出）；摘要后的 handoff 继续走主循环（带 tools）。
- 改动文件：`harbor/agents/terminus_2/terminus_2.py`（`_main_llm_call_kwargs`，只用于 `chat.chat` 两处调用）、`harbor/llms/lite_llm.py`（tool_call arguments → content）、`envarena_terminus2/settings.py`/`runner.py`（读 env、写进 harness_result raw）。

本地 driver 实测（网关 + 真实模型，3 轮小任务）：每轮 prompt_tokens 随历史推理增长（409 → 551 → 773），reasoning 进了历史，tool_call arguments 全部被 parser 正常解析，task_complete 正常。

**AB 实验（10-26 提交）**：`cth-tb21-96-dsv41-max-toolhist-2610260517`（harness 1.4.96，看得到历史推理）vs `cth-tb21-96-dsv41-max-2610260221`（harness 1.2.96，看不到）。同 benchmark `tb21-terminus2-full@2.1.3-gepa-pytorch-cache-v2`、同模型 `dsv41-flash-1017-max-chen@1.0.0`、同 2 样本 / 并发 32 / retries 1。输出在 `/storage/openpsi/users/chen/output/cth-tb21-96-dsv41-max-toolhist-2610260517/`。

线上验证（前 7 条轨迹）：取 completion ≥1500 token 的步，看下一步 `prompt_tokens` 增量是否 ≥0.9×本步 completion（即本步推理进入了下一步 prompt）。1.4.96：30/30（100%）；baseline 1.2.96（171 条轨迹）：148/2012（7%，基本只剩观察本身很长的步）。harness.log 无 parse error / 400。

## C4. 96k 设置下四种组合的正确 prompt 计数（10-26）

窗口 `CONTEXT_LIMIT=98304`，`THRESHOLD=1024`，触发线 = **97,280**。每轮循环顶部判断「下一次请求的 prompt」是否超过触发线。下一次 prompt 的正确值：

- 看得到历史推理：`P_N + C_N + 新观察`。本步推理会渲染进下一轮 prompt，所以要计入。
- 看不到历史推理：`P_N + C_N − R_N + 新观察`。R_N 是本步推理 token，下一轮不会渲染，要扣掉。

其中 P_N、C_N 是上游返回的本步 `prompt_tokens` 和 `completion_tokens`。

当前 harness（1.2.x / 1.3.96 / 1.4.96 共用同一个 `harbor/llms/chat.py`）的 usage 锚点**固定为 `P_N + C_N`**，没有按可见性扣掉 R_N。所以只有「看得到」的两格计数是对的。

| 模型 | 历史推理 | run（harness） | 上游实际渲染 | 正确计数 | 当前计数 | 重置次数 | 重置前真实 prompt p10 / p50 / p90 | 结论 |
|---|---|---|---|---|---|---|---|---|
| flash | 看得到 | `cth-csweep-c96k-flash-2610231040`（1.2.96） | 渲染 | P+C | P+C ✓ | 2,256 | 92.0k / 96.5k / 97.8k | 正确，贴着触发线 |
| flash | 看不到 | `cth-l128-nothink-flash-2610251546`（1.3.96，`INTERLEAVED_THINKING=false`） | 不渲染 | P+C−R | P+C ✗ | 572 | 81.8k / 94.4k / 97.0k | 提前触发，**需重跑** |
| dsv41 | 看不到 | `cth-csweep-c96k-dsv41-2610231040`（1.2.96，服务端丢弃） | 不渲染 | P+C−R | P+C ✗ | 485 | 83.1k / 92.8k / 97.1k | 提前触发，**需重跑** |
| dsv41 | 看得到 | `cth-tb21-96-dsv41-max-toolhist-2610260517`（1.4.96，tool-call） | 渲染 | P+C | P+C ✓ | 188 | 96.4k / 119.4k / 165.8k | 计数正确，但有冲线问题，见下 |

补充数据：

- **提前触发的比例**：用正确公式 P+C−R 重算重置前那一步的计数，flash 看不到这格有 87% 的重置其实低于 97,280，dsv41 看不到这格有 91%，也就是说这些重置本不该发生。两格各自重置前一步的推理 R_N p50 是 4.3k / 6.5k，正好是虚高的部分。看得到的两格这个比例是 0%。
- **flash 看得到这格也确认过**：98,952 个正常步里只有 1 步的 prompt 增量小于上一步的 completion，说明推理确实进了下一轮 prompt，锚点 P+C 准确。
- **dsv41 看得到（1.4.96）**：计数没错，但同一步内 prompt 会冲过触发线，原因是输出超长被截断后，截断内容直接 append 进了 history。见上一轮的诊断。剔除冲线步后，重置前 prompt p50 是 97.5k（87 次），这是正确行为；p90 159k 来自冲线。1.4.96 在 7,006 步里有 160 次突增，1.2.96 dsv41 在 50,329 步里是 0 次。
- 推理 token R_N 按 `reasoning_content` 和 `message` 的字符数占比拆分 completion_tokens 估算，没有用 tokenizer 精算。

**需要做的**：

1. chat.py 锚点改为 `P + C − (interleaved ? 0 : R)`。R 优先取上游的 `completion_tokens_details.reasoning_tokens`，没有时用本地 token_counter 估算 reasoning_content。dsv41 普通 chat 请求时，服务端会丢弃历史推理，这时也要按看不到处理，所以 interleaved 的判断要用「上游是否渲染」，不能只看 env。修复版本已写在本地 `coding_arena/build/terminus_pkg_v4/`，**还没有发布**。
2. 修复发布后，在 512 题上重跑「看不到」的两格：flash nothink、dsv41 普通 chat。1.0.1（262k 窗口的 nothink 消融）也有同样的问题。
3. 1.4.96 另外要处理截断内容污染 history 的问题，处理之前它的 p90 prompt 不能当作 96k 设置的结果。

**不同之处**：
- flash 在 1.2.96 下是「看得到」的默认行为，1.3.96 屏蔽后分数略降；dsv41 反过来，1.4.96 让它看到后分数略降。dsv41 的 1.4.96 还叠加了 tool-call 格式本身（6.4% 畸形 arguments）和冲线导致的超长 prompt 两个干扰，不能把 −0.02 全归到「看到推理」上。

- flash 看不到这格的 compact 1.8 次是 1.3.96 计数虚高（P+C 没扣 R，87% 重置提前）下的数字，正确计数后应更低。

**与 TH-3K 的对比**（DSv4-Pro 看得到自己全部历史、不压缩）：步数 53、调用/步 2.63、推理 6.7k chars/步、峰值 p50 132k。它每步发更多命令、推理介于两种模式之间；步数只有我们 dsv41-flash 的 1/2–1/3，首先是模型更强（且是只保留成功轨迹的筛选集），其次是没有压缩打断。我们任何一格的输入 token（5.5–9.9M/条）都和 TH-3K 的 7.1M 在同一量级，说明 96k 压缩并没有省输入——压缩后重新 `cat`/`ls` 的开销抵消了上下文变短。

**对数据采集的含义**：如果要训的模型推理时看得到自己的历史推理（Qwen 系默认），采集轨迹也应用「看得到」的设置（flash 1.2.96 / dsv41 1.4.96），行为分布一致：每步推理短、步数多、压缩多。TH-3K 的「每步 6.7k 推理 + 不压缩」是第三种分布。
