TerminalHorizon-3K 轨迹数据分析报告

数据路径：/storage/openpsi/users/chen/code_data/terminal_horizon/TerminalHorizon-3K/data/TerminalHorizon-3K-SFT.jsonl（1.7 GB，2852 行）。 统计口径：轨迹级统计基于全量 2852 条；token 统计基于随机 200 条样本、使用 Qwen3.5-35B-A3B tokenizer；assistant 回复内部结构统计基于随机 300 条样本（15,133 个 assistant turn）。

0. 一句话结论

这是一个纯 Terminus-2 格式的单轮-多步终端 agent 轨迹集：每条样本 = 一个任务（固定 system prompt + 任务描述）+ 几十到几百轮「assistant 输出 JSON 命令 → user 回传终端输出」的交替。 没有 system 角色、没有 tool-call 结构、没有多轮对话级 compaction/摘要；上下文从头到尾线性累积，中位数约 14 万 token，95 分位约 38 万 token。 所谓「压缩」只存在于单条终端输出层面（harness 把超过 10,000 字节的输出截断为 [... output limited to 10000 bytes; N interior bytes omitted ...]，或仅回传当前屏幕 Current Terminal Screen）， 这是环境侧行为，而不是模型侧的 context 管理。每个 assistant turn 都带 <think>...</think> 推理，推理占 assistant 字符量约 81%。

1. 数据格式

每行一个 JSON 对象，只有一个 key：conversations，值是 [{"role": "user"|"assistant", "content": str}, ...]。全部 2852 条轨迹均以 user 开头、assistant 结尾、严格交替，无 system 角色。

user固定 system prompt + Task Description + 初始终端状态→ assistant<think>…</think> + JSON{analysis, plan, commands[]}→ userNew Terminal Output / Current Terminal Screen→ …循环 N 次…→ assistantJSON + "task_complete": true→ user"Are you sure you want to mark the task as complete?"→ assistant再次确认 task_complete: true，commands 为空

1.1 第一个 user turn：system prompt（2852 条完全相同，2834 字符）+ 任务描述

system prompt 没有单独放在 system 角色里，而是直接拼在第一条 user 消息的开头。做 SFT 时需注意：如果你的 chat template 期望 system 字段，可以把 Task Description: 之前的部分切出来作为 system。

You are an AI assistant tasked with solving command-line tasks in a Linux environment. You will be given a task description and the output from previously executed commands. Your goal is to solve the task by providing batches of shell commands.

Format your response as JSON with the following structure:

{
  "analysis": "Analyze the current state based on the terminal output provided. What do you see? What has been accomplished? What still needs to be done?",
  "plan": "Describe your plan for the next steps. What commands will you run and why? Be specific about what you expect each command to accomplish.",
  "commands": [
    {
      "keystrokes": "ls -la\n",
      "duration": 0.1
    },
    {
      "keystrokes": "cd project\n",
      "duration": 0.1
    }
  ],
  "task_complete": true
}

Required fields:
- "analysis": Your analysis of the current situation
- "plan": Your plan for the next steps
- "commands": Array of command objects to execute

Optional fields:
- "task_complete": Boolean indicating if the task is complete (defaults to false if not present)

Command object structure:
- "keystrokes": String containing the exact keystrokes to send to the terminal (required)
- "duration": Number of seconds to wait for the command to complete before the next command will be executed (defaults to 1.0 if not present)

IMPORTANT: The text inside "keystrokes" will be used completely verbatim as keystrokes. Write commands exactly as you want them sent to the terminal:
- You must end every command with a newline (\n) or it will not execute.
- For special key sequences, use tmux-style escape sequences:
  - C-c for Ctrl+C
  - C-d for Ctrl+D

The "duration" attribute specifies the number of seconds to wait for the command to complete (default: 1.0) before the next command will be executed. On immediate tasks (e.g., cd, ls, echo, cat) set a duration of 0.1 seconds. On commands (e.g., gcc, find, rustc) set a duration of 1.0 seconds. On slow commands (e.g., make, python3 [long running script], wget [file]) set an appropriate duration as you determine necessary.

It is better to set a smaller duration than a longer duration. It is always possible to wait again if the prior output has not finished, by running {"keystrokes": "", "duration": 10.0} on subsequent requests to wait longer. Never wait longer than 60 seconds; prefer to poll to see intermediate result status.

Important notes:
- Each command's keystrokes are sent exactly as written to the terminal
- Do not include extra whitespace before or after the keystrokes unless it's part of the intended command
- Extra text before or after the JSON will generate warnings but be tolerated
- The JSON must be valid - use proper escaping for quotes and special characters within strings
- Commands array can be empty if you want to wait without taking action

4. 是否有 compaction？

答案：对话级别没有，输出级别有。
  • 没有模型生成的 context summary、没有 harness 插入的"Summary of previous conversation"、没有重置历史重新开始的迹象；全部 301,268 条消息都是原始交替，第一条 user 消息（system prompt + task）在每条轨迹中只出现一次，上下文一路累积到最后。
  • 有的是 Terminus-2 harness 对单条终端输出的限制：2658/2852（93%）的轨迹中出现过 [... output limited to 10000 bytes; N interior bytes omitted ...]，每条轨迹中位数 3 次，最多 13 次，总计 8,545 次。另外 34% 的反馈 turn 是 Current Terminal Screen（只回传当前屏幕，而非完整输出）。
  • 所以这份数据的"长程"来自真实累积：轨迹长度 = 真实 context 长度。这点与带 compaction 的 Claude Code / OpenCode 风格数据有本质不同：模型在这里学到的是"在超长 context 内保持状态"，而不是"在摘要后恢复状态"。

6. 对用 LlamaFactory 做 SFT 的直接影响

6.1 数据转换

  • 格式是 conversations: [{role, content}]，对应 LlamaFactory 的 sharegpt 格式，需在 dataset_info.json 里配 "formatting": "sharegpt"，"columns": {"messages": "conversations"}，"tags": {"role_tag": "role", "content_tag": "content", "user_tag": "user", "assistant_tag": "assistant"}。
  • 可选：把第一条 user 的 Task Description: 之前部分切为 system 消息。不切也能训，但推理时 prompt 组织方式要和训练一致。
  • assistant 内容是 <think>…</think>JSON 纯文本，不是 tool-call 结构；不要用 function-calling 模板，普通 chat 模板即可。对于 Qwen3 系列，模板自身会处理 <think> 标签（注意 Qwen3 模板在多轮时默认会剥掉历史 turn 的 think，看是否符合你的目标：论文设定是保留全部推理还是只保留最后一轮，需要在 template 里确认）。

6.2 序列长度是最大的工程问题

  • 中位数 14 万 token、P95 38 万、最大 88 万+。cutoff_len 设 32K/64K 基本等于把每条轨迹都砍掉大半，而且砍掉的是结尾（task_complete、确认、最终验证）。
  • 可行策略：(a) 上 128K–256K 的 cutoff + sequence parallel / ring attention + packing；(b) 对超长轨迹做滑窗切分，每个片段 = system+task + 从某个 turn 开始的连续片段（需自己构造，数据中没有现成的摘要可以做 anchor）；(c) 直接过滤掉 >128K 的 ~55% 轨迹只训短的（会损失最"长程"的样本，与数据集的卖点相悖）。
  • 如果切分，建议以 user turn 为边界，保证每个片段的第一条是 user、最后一条是 assistant。

6.3 loss mask 建议

  • 只对 assistant 计算 loss（默认即可）。
  • 可选清洗：紧跟 Previous response had parsing errors 的那个 assistant turn 是非法 JSON（458 个），建议 mask 或删除；Previous response had warnings（3,461 个）对应的 assistant 是轻微格式问题，可保留。
  • 33 条轨迹的最后一个 assistant turn 不是 task_complete:true（可能被步数上限截断），可考虑过滤。

6.4 行为模式（模型会从这份数据学到什么）

  • 先 ls -la + xxx --help 探索环境，再逐个子命令 --help，再 cat 所有数据文件——非常稳定的开局套路。
  • 一个 turn 批量发 2–3 条命令，用 0.1s/0.5s/1.0s 的 duration，很少一次发太多。
  • 遇到输出被截断/只见屏幕尾部时，改为 cmd > /tmp/x.json; python3 -m json.tool /tmp/x.json | head -n 120 或写 heredoc python 脚本做结构化查询——17% 的命令是 heredoc。
  • 收尾模式固定：跑 validate/check → 给 task_complete:true → 收到 "Are you sure" → 空 commands 再确认。
  • think 风格是高度压缩的电报体，而非自然语言长推理；若你的目标模型 think 风格不同（如 Qwen3 的完整句子），混训时要注意风格冲突。
